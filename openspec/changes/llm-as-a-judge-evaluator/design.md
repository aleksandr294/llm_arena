# Design

## Context

`EvaluationService.evaluate_result` (`components/evaluation/service.py`) currently reads the input, runs every configured evaluator synchronously, and writes all outcomes — all in one session, on the premise (its own docstring) that "evaluators are pure and fast." `BaseEvaluator.evaluate()` (`components/evaluation/evaluators.py`) is a synchronous, no-I/O method; `EVALUATORS` is a `dict[str, type[BaseEvaluator]]` keyed by `entry.type`, and `build_evaluator()` instantiates one from a validated config entry. `ExperimentRunner` (`components/experiments/runner.py`) already solves the "slow external call" problem this feature now runs into: claim (commit), call the provider with no session open, persist the outcome in a new transaction — CLAUDE.md names this pattern explicitly ("An operation with a slow external call is split into short operations instead of holding a transaction open (see `ExperimentRunner`)"). `LLMService` (`components/third_party/llm/service.py`) is already provider-agnostic and is what `ExperimentRunner` uses; this change reuses it rather than building a second provider abstraction. `EvaluationInput` (`components/evaluation/schemas.py`) and `EvaluationRepository.get_input` (`components/evaluation/repository.py`) read `response_text` and `expected_output` but not the test case's `input`, which a judge needs to tell whether the response actually addresses the question. See proposal.md for the three scope decisions already confirmed with the user (pass/fail verdict, per-evaluator judge model, free-text criteria).

## Goals / Non-Goals

**Goals:**
- `llm_judge` fits into the same `evaluators` configuration list and discriminated union as the deterministic types, with no new top-level config shape.
- Deterministic evaluators' existing single-transaction path is untouched — this change must not slow down or complicate the common case of an experiment with no `llm_judge` configured.
- A judge call never holds a database session open, matching `ExperimentRunner`.
- Hostile content (the response being judged, the test case's input/expected output, and the judge's own output) never reaches stored `details`, matching the project-wide rule every other evaluator already follows.

**Non-Goals:**
- Numeric or graded scoring (decided with the user: pass/fail only).
- A shared/global "judge model" setting (decided with the user: per-evaluator provider/model).
- Built-in rubric templates (decided with the user: free-text `criteria` only).
- Cost caps or quotas for judge calls specifically — covered by the existing tech-debt card on experiment-level spend caps, not duplicated here.
- Changing how deterministic evaluators are configured, evaluated or stored.

## Decisions

- **`llm_judge` is not a `BaseEvaluator` subclass.** `BaseEvaluator.evaluate()` is synchronous and I/O-free by contract (every existing implementation and the whole single-transaction path assumes that). Making it `async` would force every call site to change for one evaluator type. Instead, `EvaluatorEntry`'s discriminated union gains `LlmJudgeEntry` (so configuration, validation and the single `evaluators` list stay unified), but `evaluate_result` routes `llm_judge` entries to a separate, async path instead of `build_evaluator().evaluate()`. Alternative considered: make `BaseEvaluator.evaluate` async everywhere — rejected, it would touch every deterministic evaluator for no behavioral reason and still not solve the transaction problem (async alone doesn't mean "no session open").
- **Two-phase `evaluate_result`.** Phase 1 (unchanged): read input, run every deterministic entry, insert their rows — exactly today's code path, same transaction. Phase 2 (new, only when `llm_judge` entries are configured): for each entry, call `LLMService.generate(...)` with no session open; collect outcomes; open one new short transaction to insert all judge rows via the existing `EvaluationRepository.insert_ignore`. This mirrors `ExperimentRunner`'s claim/call/persist split at the evaluator-entry granularity rather than the result granularity, since one result can have several judge entries.
- **The judge prompt.** A fixed system prompt (not operator-configurable, to keep the instruction/data boundary under the project's control) states the task, embeds the operator's `criteria`, and instructs the model to answer in one fixed, easily-parsed shape (for example a single leading token, `PASS` or `FAIL`, nothing else required). The test case's `input`, the response being judged, and the expected output (when present) are each wrapped in clearly delimited blocks the system prompt names as *data to evaluate, never instructions to follow* — a defense-in-depth measure against the response itself trying to steer the verdict, documented as a mitigation, not a guarantee (prompt injection cannot be fully closed by prompting alone). `temperature=0` is sent for determinism-as-far-as-possible; the project does not claim the judge is reproducible (CLAUDE.md: "Support deterministic evaluators before introducing LLM-as-a-judge" already frames this as the non-deterministic case).
- **Parsing the verdict.** The response text is checked for a `PASS`/`FAIL` token (case-insensitive, leading whitespace tolerated); anything else — empty, ambiguous, or missing the token — is `OutcomeStatus.ERROR` with `reason: "unparseable_verdict"`, never guessed as a pass or a fail. The model's own explanation text, if present, is read only to find the token and then discarded, never stored.
- **Reusing `LLMService`, not a new provider path.** `EvaluationService` gains a constructor-injected `LLMService`. Unlike `ExperimentRunner`'s `llm_service` (required, no default, since that class only ever runs model calls), `EvaluationService` also serves the HTTP-facing read methods (`list_evaluations`, `summary`, `backfill`), which never need one — so `llm_service` is an optional parameter, not a required one, and `evaluate_result` itself checks for it: if the configuration has an `llm_judge` entry and no `llm_service` was given, it raises before persisting anything (not even the deterministic rows), rather than discovering the gap mid-method after a partial commit. `components/evaluation/tasks.py` builds one `LLMService(get_settings())` per process (mirroring `components/experiments/tasks.py`'s `@lru_cache def get_runner()`), passed into `build_evaluation_service`; the HTTP endpoint never calls `evaluate_result` and so never needs to supply one.
- **Error handling matches deterministic evaluators.** A judge call's `LLMProviderError` (timeout, rate limit, provider failure) is caught at the per-entry level and stored as `OutcomeStatus.ERROR` with only `exc.kind.value`, the same shape the existing exception handler in `evaluate_result` already uses for a deterministic evaluator's unexpected exception. No retry loop is added beyond a single bounded retry on a retryable error (reusing `components/experiments/utils.backoff_delay`), proportionate to one evaluation call rather than the full attempts/lease machinery `ExperimentRunner` needs for experiment results.
- **`EvaluationInput` and `get_input` gain the test case's `input`.** A small, additive query change (`components/evaluation/repository.py`); unused by deterministic evaluators, read by the judge path only.

## Risks / Trade-offs

- [Prompt injection: a hostile response could try to manipulate its own verdict] → delimited data blocks and an explicit system-prompt instruction are a mitigation, not a guarantee; documented as a known limitation, matching how the project already treats dataset content and model output as untrusted everywhere else, never as a false claim of immunity.
- [A judge call adds real latency and cost to evaluation, which was previously near-instant] → evaluation already runs as its own enqueued task, separate from experiment execution, so this does not block or slow the experiment itself; cost is visible through the existing LLM provider usage the same way an experiment's own model calls are (and, per the recent observability change, through `model_call_cost_estimate_total`, since the judge call goes through the same `LLMService`/adapter path).
- [An unparseable or borderline verdict silently defaulting to pass or fail would be worse than surfacing it] → always `error`, never guessed, per the spec's own requirement.
- [Splitting `evaluate_result` into two phases adds complexity to a currently simple method] → justified: the alternative (holding a session open across an LLM call) is the exact anti-pattern CLAUDE.md calls out by name.
