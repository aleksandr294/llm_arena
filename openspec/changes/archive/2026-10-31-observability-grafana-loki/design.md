# Design

## Context

No logging configuration exists anywhere in the app (`grep` for `basicConfig`/`dictConfig` across `main.py`, `taskiq_app.py`, `api/app.py` finds nothing); each module calls `logging.getLogger(__name__)` and the API container's default handler is whatever Python's logging defaults to. `api/middleware.py` already shows the project's pattern for ASGI-level cross-cutting concerns (pure ASGI, not `BaseHTTPMiddleware`, because that interferes with streaming and background work). `taskiq` 0.13.0 ships `TaskiqMiddleware` with `pre_execute`/`post_execute`/`on_error` hooks, which is the project's existing extension point for the worker. `components/metrics/pricing.py` already has the pure cost-estimate function used for experiment CSV export; this change reuses it rather than re-deriving pricing logic. (Implementation note: reusing it from `ExperimentRunner` made it a name used by two components, which CLAUDE.md's "one home" convention puts in `components/core` — it moved to `components/core/pricing.py` with `PricingConfigError` in `components/core/exceptions.py`, and `components/metrics/service.py` updated to import from there; see the Decisions entry below.) `docker-compose.yml` already has the `x-app-environment`/`x-app` anchor pattern and binds every infra port to `127.0.0.1` except the published `api` port — the new services follow the same binding rule. See proposal.md for the Kan card and the TTFT scope decision (confirmed with the user: approximate generation speed now, real streaming-based TTFT is tracked as separate tech debt).

## Goals / Non-Goals

**Goals:**
- Every log line is structured JSON with no prompt, model output, key or secret content.
- The six signals from the Kan card are all exposed except true TTFT, which is replaced by an explicitly-labeled approximation per the proposal's scope decision.
- Grafana, Loki, Prometheus and Promtail run locally via Compose, each bound to localhost, with Grafana pre-wired to both data sources so a developer does not configure them by hand.

**Non-Goals:**
- No streaming support in the LLM provider adapters (tracked separately).
- No alerting rules, no production-grade retention tuning, no dashboards beyond one minimal starter dashboard proving each of the five in-scope signals is queryable.
- No change to `components/metrics` (experiment-level CSV/summary metrics) — this is a different, operational concern.

## Decisions

- **`prometheus-client` for metrics, pulled, not pushed.** The API exposes `/metrics` (an unauthenticated, no-store, non-versioned ops endpoint, consistent with `/health`); the worker, which has no HTTP listener, exposes `/metrics` too via `prometheus_client`'s small `start_http_server` on a separate port, since Prometheus can only scrape HTTP. Alternative considered: push via `pushgateway` — rejected, pull is the library's and Prometheus's default mode and needs no extra service for a single worker replica.
- **Structured logging via stdlib `logging` + a JSON formatter, not a new logging framework.** A `logging.config.dictConfig` applied once at process start (API and worker both call it) with a formatter that emits one JSON object per line (timestamp, level, logger, message, and any `extra=` fields). Alternative considered: `structlog` — rejected as an unjustified new dependency per CLAUDE.md; stdlib logging with a formatter covers everything Loki/Promtail need (Promtail reads container stdout, not a special protocol).
- **HTTP metrics as pure ASGI middleware**, following `SecurityMiddleware`'s existing shape, added alongside it in `api/app.py`. Counts responses by status and records latency; wraps the whole chain in try/except like `SecurityMiddleware` does, so an unhandled exception still increments the 500 counter before the generic handler responds.
- **Task metrics as a `TaskiqMiddleware`**, registered on `broker` in `taskiq_app.py`. Taskiq's own receiver already catches every exception raised inside a task and turns it into `TaskiqResult(is_err=True, error=exc, execution_time=...)` before calling `post_execute(message, result)` — it never re-raises to a middleware. So one hook, `post_execute`, is enough: it reads `result.execution_time` for latency and `result.is_err` for the success/failure counter, labeled by `message.task_name`. This sits outside `ExperimentRunner`'s own per-result bookkeeping (status, retries) — it measures the Taskiq task invocation itself, not business outcome, so duplicate delivery (a documented platform property) can legitimately double-count a task metric; the metric is operational, not a source of truth the way the stored `Result` row is.
- **Model call metrics recorded where the measurement already exists**: `LLMResponseSchema` already carries `latency_ms` and `usage`. Rather than threading Prometheus calls into every provider adapter (which would spread an operational concern into `components/third_party/llm`, against CLAUDE.md's "no abstraction leakage" layering), the metric is recorded once, in `ExperimentRunner`, right after a provider call returns — the one place that already sees every request's response and the model/provider labels. Generation speed is derived there as `usage.output_tokens / latency_ms` when both are present, else omitted. Cost reuses `components/core/pricing.py`'s existing function (moved there from `components/metrics/pricing.py` — see the Context note above) with the already-loaded pricing file; when pricing is unset or the model is unlisted, the cost metric for that call is skipped rather than recorded as zero.
- **No sensitive data in any new log or metric label.** Labels are bounded (provider, model, HTTP route, HTTP status, task name) — never a raw prompt, request id used as a label (unbounded cardinality is a Prometheus anti-pattern anyway), or free-text error message. Error detail stays in the existing `LLMProviderError.kind`, not in a metric label.
- **New Compose services `loki`, `promtail`, `prometheus`, `grafana`**, dev-only, each with ports bound to `127.0.0.1` (same rule the project already applies to `postgres` and `rabbitmq`). Promtail reads the `api` and `worker` containers' JSON stdout via the Docker logging driver and ships to Loki; Prometheus scrapes `api:8000/metrics` and a new worker metrics port; Grafana's datasources are provisioned from a checked-in YAML file (declarative, not clicked through by hand), so the stack is reproducible.

## Risks / Trade-offs

- [Generation speed from total latency, not time-to-first-token, understates how a user perceives responsiveness for long generations] → labeled explicitly as an approximation in the metric name/help text and in `docs/observability.md`; real TTFT is a tracked follow-up.
- [Worker needs a second open port for its own `/metrics`, which the current Compose file does not expose] → bind it to `127.0.0.1` like every other infra port; document it; no change to the worker's task-handling behavior.
- [`TaskiqMiddleware.post_execute` itself must not raise, or it could break the receiver loop] → covered by a unit test that runs a task through a real broker with an in-memory result backend, forces an exception inside the task, and asserts the task's `TaskiqResult.is_err` is `True` and the failure counter still increments.
- [Adding `prometheus-client` is a new dependency] → justified: it is the de facto standard client for exactly the metrics this card asks for, and no existing library in the project does this job.
- [Promtail's `docker_sd_configs` needs `/var/run/docker.sock`, mounted read-only; `:ro` only blocks writes to the socket *file*, not which Docker Engine API calls can be made over it once connected — daemon-socket access is effectively root-equivalent host access regardless] → accepted for this dev-only, localhost-bound stack (see `docs/security.md`'s findings register); not accepted for a production deployment. A socket-proxy sidecar (e.g. a read-only Docker API proxy) would remove this if the stack is ever used beyond local development.
